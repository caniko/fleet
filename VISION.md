# fleet vision

`fleet` is an integration superproject for the owned fleet-management
components — fleetix, canix-toolbelt, infernix, nix-manager-core,
secret-manager, dns-manager, bootswain, and ignitix. Each component stays in its
own repository with its own releases; this repository pins them as gitlinked
submodules and qualifies the pinned revisions together in CI.

## Problem

Components that are released independently can be individually green and still
incompatible in combination. Consumers otherwise discover that after pinning
them, when the failure appears in the consumer's build rather than in a gate
that owns the combination.

## Principles

- Components keep their own repository, package identity, and release. Fleet
  only moves gitlinks.
- Qualify the producer revisions consumers will actually ship: sibling flake
  inputs follow the gitlinked checkout, so CI tests the pinned set rather than
  floating branches.
- Qualification gates the merge. A component change opens a fleet pull request
  that moves its gitlink to the component head, and the component merges once
  fleet's `qualified` check passes.
- CI is generated by Simit from `simit.toml`; the component list, paths, Cargo
  packages, and checks are declared there instead of hand-written workflows.
- Publication stays with the component repositories; this repository's CI
  qualifies, it does not publish.

## Scope

Eight gitlinked components under `components/`, the root flake that supplies
their shared inputs (harbor-rs, nixpkgs, plinth, nix-pklx, simit for CI), the
`simit.toml` monorepo component and check declarations, and the generated
GitHub Actions workflows.

## Non-goals

Fleet is not a package registry or release train and does not own component
versioning. It also does not replace a component's own CI; it tests the
combination the component's own pipeline cannot see.

## Direction

The recent history is the integration gate doing its job: add a component
(ignitix was added after the initial set), point gitlinks at merged component
trunks, and qualify component heads before landing them.

## Place in the fleet

Canix does not consume `fleet` as a flake input; it consumes the components
directly (for example `fleetix`, `dns-manager`, and `harbor-rs` are separate
inputs). Fleet is the gate that certifies those component revisions are
compatible before canix pins them.
